# Rent Check HOME 공통 작성·발행 기준

HOME의 직접 작성하는 가이드와 편집형 분석 글에 적용하는 단일 기준이다. 작업 시작 전에 이 파일과 최신 main의 관련 기존 글을 읽는다. 정상 작성·업로드·예약 방식, 기존 템플릿과 발행 경로를 유지한다. 네이버 글·자동 공고 수집은 별개이며, 이 문서로 그 생성기나 스케줄을 변경하지 않는다.

## 작성 전에 확인할 것

1. 독자가 해결하려는 질문을 한 문장으로 정하고 첫 문단에서 직접 답한다. 조건이나 예외가 답을 바꾸면 함께 밝힌다.
2. `blog/`, 편집형 `analysis/`, `/blog/`, `/blog/all/`의 실제 기존 제목과 본문을 확인해 검색 의도 중복을 비교한다. 키워드가 달라도 같은 질문·대상·판단 단계·기준일을 다루면 기존 글 보완을 먼저 검토한다. 기존 글을 읽지 않은 채 중복 없음이라고 보고하지 않는다.
3. 법률·금융·자격·한도·기한·공고·거래 수치 등 근거가 필요한 주장은 관련 공식 원문과 대조한다. 원문 URL, 해당 조항·항목, 적용 기준일, 실제 확인일과 확인 범위를 기록한다. 기관 홈페이지 링크만으로 개별 주장을 검증했다고 간주하지 않는다.
4. 원문 접근 제한, 특정 공고 미확인, 과거 기준 미확인은 그대로 밝힌다. 제목이나 검색 결과만 보고 출처를 추정하지 않는다. 현재 원문을 확인했다고 과거 조건이나 변경 시점까지 확인한 것으로 쓰지 않는다.

## 본문과 원자료

- 확인된 사실, 원자료에서 계산한 값, 설명용 가정과 예시를 구분한다. 원자료 누락·수집 실패·미확인 상태를 거래 0건이나 모집 0명으로 바꾸지 않는다. 0은 해당 기간·대상에서 실제로 확인된 0일 때만 쓴다.
- 수치에는 기간, 지역·대상, 단위와 집계 기준을 붙인다. 계산식과 주요 제외 조건을 확인하며 자료의 한계를 결과와 함께 설명한다. 오래된 통계를 현재 통계처럼 다시 소개하지 않는다.
- 공식 원문 링크는 해당 주장 또는 기존 출처 영역에 붙인다. 출처 일부만 확인했으면 확인한 범위만 표시한다. 자체 계산은 입력·가정·계산 방법을 밝히고 관련 없는 공식 링크로 포장하지 않는다.
- 고정 글자 수를 공식 SEO 기준이나 승인 조건처럼 강제하지 않는다. 기존 길이 검사는 참고 지표이며, 질문에 충분히 답하는지가 우선이다. 분량을 채우는 반복 문장, 관련 없는 표·이미지·링크를 추가하지 않는다.
- 외부 SEO 자료는 검토 참고로만 사용한다. 자료를 참고하는 것은 플러그인·스크립트 설치나 실행, 권한 부여, 기존 자동화 변경의 승인이 아니다.

## HTML과 목록 등록

- 현재 글의 HTML 템플릿, 글꼴·크기, 표, 목록, 공통 CSS, 모바일 구조, 통계·분석·광고 코드를 보존한다. SEO 문구를 고치려고 공통 템플릿이나 전체 글을 다시 생성하지 않는다.
- 기존 대표 URL을 유지한다. 새 글은 기존 발행 경로에서 URL을 정하고 title, meta description, H1, canonical과 구조화 데이터가 실제 내용·URL·날짜에 맞는지 확인한다. title은 질문과 답을 분명히 하고, meta는 본문에서 제공하는 내용을 정확히 요약한다.
- 관련 글 링크는 독자가 다음으로 확인할 질문과 직접 관련된 기존 글로 연결한다. 도구가 특정 공고 전용이면 해당 공고의 조건·시점에 맞게 안내하고 현재 사용 가능한 범용 도구처럼 홍보하지 않는다.
- 기존 등록 방식으로 `/blog/`, `/blog/all/`와 사이트맵의 포함 여부를 확인한다. 사이트맵이 인덱스이면 참조된 자식 파일까지 확인한다. 목록 또는 공통 파일 전체를 재생성해 다른 등록 항목을 덮어쓰지 않는다.
- HOME 가이드 수, 네이버 발행 수, 거래 수, 공고 수는 서로 다른 지표다. 기존 정의와 원자료를 유지하고 새 HOME 글 때문에 관련 없는 통계를 임의로 늘리거나 고치지 않는다.

## 로컬 검수와 발행 뒤 확인

1. diff에서 승인된 파일·문장만 바뀌었는지 확인한다. 최신 main과 자동 갱신을 보존하고 다른 작업의 변경을 합치지 않는다. force push를 하지 않는다.
2. 가이드의 읽기 전용 발행 검사는 `python scripts/audit_seo_publication.py --article blog/<slug>/index.html`로 확인한다. 전체 검사는 `python scripts/audit_seo_publication.py`, 내부 링크는 `python scripts/audit_internal_links.py`로 확인한다. 이 검사는 모든 본문 주장이나 실제 운영 응답·색인 상태를 보증하지 않는다. 실패·미확인 결과를 성공으로 보고하지 않는다.
3. 기존 PC·모바일 화면에서 글꼴, 표·목록, 줄바꿈·가로 넘침, 링크와 JS 오류를 확인한다. 브라우저 뷰포트 검사와 실제 기기 검사를 구분해 기록한다.
4. 기존 발행 흐름으로 반영한 뒤 실제 본문, `/blog/`, `/blog/all/`, 대표 URL·사이트맵과 관련 통계를 확인한다. 변경 커밋, 실제 배포 커밋·CI 결과, 운영 본문·링크·화면 확인을 구분해 보고한다. 저장소에 올렸다는 사실만으로 운영 배포나 검색 색인·순위 향상이 완료됐다고 하지 않는다.

## 이 기준을 읽었다는 증거

기존 작업 기록에 읽은 파일 경로 `docs/home-content-guidelines.md`, 당시 커밋과 적용한 핵심 항목을 남긴다. 별도 전달 체계나 중복 파이프라인을 만들지 않는다. 루트 [AGENTS.md](../AGENTS.md)는 저장소 작업자의 진입 안내이고, [기존 콘텐츠 보강 계획](content-enrichment-20260908.md)은 이 기준을 참조한다.

외부 예약 작성기가 어느 저장소 문서나 입력을 읽는지 확인되지 않았다면 연결 완료라고 표현하지 않는다. 다음 실제 예약 실행의 읽기 기록, 생성·업로드 결과와 발행 화면을 확인하는 일은 별도 단계다. 이 파일 추가만으로 기존 예약 프롬프트나 생성기의 동작이 자동으로 바뀐다고 가정하지 않는다.
